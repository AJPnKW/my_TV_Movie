Note: counts are per distinct incident where that cause (or fix) was the real reason, not how many times we talked about it.

#	Root Cause	Times It Was The Actual Fix	Where It Showed Up
1	Parser expectations vs file content	2	(a) movies_list.txt line format / separators; (b) hidden/odd formatting causing movies to be skipped.

Open /data/data.json → check "movies" count.

If 0:

2. Movies disappeared again – let’s talk root causes properly

You’re right: saying “it was exactly 3–4 times” is too shallow. Pattern-wise, across everything you’ve described, the failures cluster into a few recurring classes (sometimes overlapping in the same incident):
Class A – Input format / parser mismatch

Examples:
    Separator lines (-----), rich comments, or stray characters treated as data.
    Headers or version lines added without the parser explicitly skipping them.
    Encodings / line endings (copying from Word/HTML/raw view adds hidden junk).
Effect: fetch_tmdb.py quietly skips those lines → valid entries count = 0 → data.json written with "movies": [] → UI “no movies”.

This is the one that has bitten you multiple times (more than two), in different flavors.
Class B – Wiring / naming drift
    Workflow or script temporarily pointed at:
        The wrong filename (movies.txt vs movies_list.txt).
        The wrong relative path (./movies_list.txt vs repo root vs data/).
    Renames like fetch_live_tv_stub.py → fetch_live_tv.py without updating the workflow in sync.
Effect: Build runs “fine” but script never sees any movie rows → "movies": [].

Happened at least once clearly, likely contributed in combination to others.
Class C – “Successful” bad builds overwriting good data
    Python exits 0 (no crash), but logic produced empty/partial arrays due to A/B.
    build-data.yml then:
        Uploads and deploys that data.json.
    Frontend is correct, but it’s rendering exactly what it’s handed: an empty movies list.

This has happened at least twice: once with no movies, once with partial regressions.
Class D – Frontend schema mismatch (less frequent, but real risk)
    Index expecting fields that aren’t always present:
        e.g., using mv.name vs mv.title, or assuming runtime/belongs_to_collection.
    If we filteed or dereferenced based on a missing field, a sloppy check could hide valid entries.

We’ve mostly avoided this, but every time we refactor index.html without re-checking data.json, it’s a potential cause.
