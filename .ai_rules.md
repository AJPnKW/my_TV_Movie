Purpose:
This file defines the hard operating constraints for AI and Codex work in this repository.

## Hard Environment Constraints

1. Windows shell and patch payload size limits apply.
2. Large artifact writes must be chunked.
3. Never assume a single large patch or write is safe.
4. Prefer multiple append or staged writes over one oversized payload.
5. Any artifact larger than approximately 3 KB or 150 lines should be treated as a batched write.
6. Any artifact larger than approximately 20 KB requires mandatory staged writes plus validation.
7. If a write fails, retry with smaller chunk sizes rather than repeating the same large write.

## Hard Repo Execution Rules

1. GitHub and local repo content are source of truth.
2. Never rebuild architecture from scratch when updating existing UI or logic.
3. Preserve file paths, IDs, selectors, data-* hooks, and existing working contracts unless the task explicitly authorizes breaking changes.
4. Do not mass-refactor production pages during analysis or mockup phases.
5. For UI standardization work, complete discovery, audit, mockup, reuse mapping, and validation before implementation refactor.
6. For large report artifacts, prefer CSV for large matrices and shorter Markdown summaries that point to CSV.
7. Validate every created file:
   - path exists
   - non-empty
   - readable
8. Log what was created and validated.
9. Never claim completion if required files are missing.
10. If a task cannot finish in one large write, continue in smaller batches instead of restarting.

## Large Write Policy

When generating files larger than approximately 3 KB:

1. Create the file first.
2. Write a header or first section.
3. Append remaining sections in small batches.
4. Validate file existence and size after final write.
5. Do not attempt one-shot large heredoc or patch writes.

Preferred maximum safe write size per operation:
- target approximately 2 KB to 4 KB
- use smaller chunks if previous writes failed

## Preferred Artifact Patterns

1. Large matrix:
   - write CSV as primary artifact
   - write Markdown summary as secondary artifact
2. Long HTML mockup:
   - write standalone HTML file in sections
3. Long Markdown report:
   - split by headings and sections during write
4. Logs:
   - always create execution.log.txt
   - always create summary.txt

## Recovery Rules

If command-size or patch-size limits are hit:

1. Do not restart the task.
2. Do not re-run broad discovery unless required.
3. Continue from existing completed artifacts.
4. Split the remaining file writes into smaller batches.
5. Validate only the missing outputs.
6. Return final handoff only after required outputs exist.

## UI Component Standardization Rules

For this repo's card and popup work:
1. Preserve current behavior while standardizing structure.
2. Preserve modal IDs and data-* selectors in the first implementation pass.
3. Standardize popup behavior before grid cards.
4. Centralize fallback logic before broad card swaps.
5. Keep clearly page-specific variants local where needed.
6. Use shared helpers only where reuse is proven by audit evidence.

## Output Style Rules

1. Use tables heavily for comparison artifacts.
2. Be explicit about:
   - source file
   - render function
   - selector or hook
   - data fields
   - actions
   - shared versus local decision
3. Do not collapse meaningful differences into vague summaries.
4. Distinguish:
   - baseline shared
   - shared with variation
   - page-specific local
   - out of scope

## Completion Rules

A task is complete only when:
1. All required files exist.
2. All required files are non-empty.
3. Validation is complete.
4. Logs are written.
5. Final response matches the requested structure.
